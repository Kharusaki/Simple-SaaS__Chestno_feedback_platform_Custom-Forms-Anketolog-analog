**Проверено:**

- Живой прогон на uvicorn (порт 8002): `GET /surveys/new` → 200;

  `GET /dashboard` с той же сессией → 200, опрос в списке, счётчик «5 вопросов».
- `python -m database.init_db --report`: users 1, surveys 1, questions 5,

- Выборка из БД подтвердила все 5 типов: `single` с 3 вариантами, `multiple`
  с 2, `yes_no` без вариантов, `scale` 1–10, `text`; ключ «основной доступ»,
  `can_edit=True`, токен 48 символов.
- Каскад проверен тестом: удаление опроса уносит его вопросы.

**Найдено и исправлено (2 реальных бага):**

1. **FastAPI терял cookie владельца.** Заголовки из DI-параметра `Response`
   переносятся в ответ только когда эндпоинт возвращает **не** `Response`
   (`routing.py:133`, ветка `else`). Мои роутеры возвращали `TemplateResponse`,
   поэтому `set_cookie` на инъецированном объекте просто исчезал. Проверено
   по исходнику установленной версии FastAPI, а не по догадке.
   **Исправлено:** cookie ставится из `request.state` в `deps.render()` и
   `deps.apply_owner_cookie()`.
2. **Первый созданный опрос «терялся».** Следствие бага №1: на редиректе
   `303` после `POST /surveys/new` cookie не ставилась, следующий запрос
   создавал нового анонимного пользователя, и дашборд был пуст. Пользователь
   увидел бы пустую страницу сразу после создания опроса.
   **Исправлено:** `apply_owner_cookie()` вызывается и на редиректе; редирект
   сделан относительным, чтобы не зависеть от заголовка `Host` за прокси.
   Оба случая закрыты регрессионными тестами.

**Решения:**

- Форма конструктора рендерится **на сервере** (Jinja2), JS только добавляет и
  удаляет блоки. При ошибке валидации введённый текст и варианты сохраняются
  через `BuildResult.raw_blocks` — пользователь не теряет работу.
- Номера полей в форме — `q<N>_*`, `N` сквозной с нуля. При ошибке ключ
  ошибки привязан к **позиции блока**, а не к исходному номеру поля, поэтому
  сообщения попадают в правильный вопрос.
- Пустые вопросы не «съедаются молча», а дают ошибку по конкретному блоку.
- Число вопросов/ответов в дашборде считается двумя агрегирующими запросами на
  весь список, а не в цикле по опросам.
- `deps.py` импортирует `auth.tokens`: цикла нет (`auth.tokens` не знает про
  шаблоны), зависимость однонаправленная.

- Живой прогон: `GET /s/f8ghkzwt` **без cookie** → 200, 5 блоков вопросов,
  cookie не выдаётся публичной странице.
- `POST /s/{slug}` → 303 → `/s/{slug}/thanks`; страница «спасибо» → 200.
- Повторная отправка с того же устройства → **409**, страница

- Неизвестный slug → **404**.
- Выборка из БД подтвердила все 5 типов и **два ряда `multiple` на один вопрос**:
  `pos 1 multiple -> 'API'` и `pos 1 multiple -> 'Веб-интерфейс'`.
- Каскад проверен: удаление `responses` уносит `answers`.

**Найдено и исправлено (1 ошибка теста, 1 уточнение):**

- Мой тест `test_answers_are_linked_to_questions_of_this_survey_only` падал с
  `UNIQUE constraint failed: users.token` — фикстура владельца использовала
  фиксированный токен и вызывалась дважды за тест. Заменено на счётчик.
- В ходе ручной проверки `multiple` сначала выглядел как сломанный: PowerShell
  `-Body @{q2=@("API","Веб")}` **склеивает** массив в одно значение. Это
  особенность PowerShell, а не приложения. Перепроверено настоящим
  urlencoded-телом через `httpx` — два ряда сохраняются корректно.
- Анти-дубль по `respondent_hash` оказался строгим: два разных PowerShell-сеанса
  с одинаковыми IP и User-Agent получили один хеш. Это ожидаемое поведение
  (устройство = ip+ua) и будет описано в README как известное ограничение:
  за общим NAT или корпоративным прокси опрос пройти нельзя.

**Решения:**

- Обязательность вопроса **не блокирует** отправку формы: она влияет на
  статистику, но не на приём ответа. Иначе одна ошибка в одном вопросе
  отбрасывала бы весь ответ респондента.
- `Response.submitted_at = NULL` — брошенная сессия, она не участвует в
  анти-дубле и не попадает в статистику. Поле оставлено как точка входа
  для будущего сохранения черновика, но логики вокруг него нет.
- Хеш респондента — `sha256(ip + ua + SECRET_KEY)`: в БД не попадает ни IP,
  ни User-Agent, но хеш нельзя перебрать без знания секрета.
- Публичная страница не ставит cookie владельца: иначе каждый случайный
  посетитель порождал бы строку в `users`.

  `line 1..10 = [0,0,0,1,0,0,1,0,0,1]`.
- CSV: `text/csv`, BOM на месте, `filename*=UTF-8''...` содержит кириллицу,
  три строки — по одной на респондента, пропуски пустые, `multiple` склеен
  через запятую.
- Пустая статистика → экран «Ответов пока нет» с готовой ссылкой.
- Чужой браузер → **403** и HTML-страница (не JSON).

**Найдено и исправлено (1 настоящий баг приложения, 2 ошибки теста):**

- **Баг: строки CSV и «последних ответов» смешивали респондентов.** В выгрузке
  каждая строка содержала ответы **всех** участников подряд:
  `Отлично, Отлично, Хорошо`. Причина — `answers_for_questions()` группирует
  ответы только по `question_id`, но не фильтрует по `response_id`, а
  строка CSV строится по конкретному респонденту. То же самое было в таблице
  последних ответов. Добавлен `answers_for_responses()` и ключ
  `(response_id, question_id)`.
  Тесты это не ловили: в них был **один** респондент, а при одном
  респонденте смешение невозможно. Добавлены два теста с двумя респондентами —
  один на последние ответы, один на CSV.
- Ошибка теста: `OptionStat.percent` был `property`, а в него писали через
  `_apply_percent`. Заменено на обычное поле.
- Ошибка теста: забыл `delimiter=";"` при чтении CSV обратно, и фабрика
  не умела принимать `title`.

**Решения:**

- `answers_for_questions()` оставлен для честных сводок (там смешивать
  респондентов и надо) и задокументирован — «для строки конкретного
  респондента нужен `answers_for_responses`».
- Сводка и CSV используют разные группировки специально: статистике нужны
  все ответы сразу, выгрузке — по одному респонденту на строку.
- Проценты в вариантах считаются от `answered`, а процент ответивших — от
  всех ответов. Иначе при 100 % пропусков график показывал бы 0 % у всех.
- Формулы вида `=1+1` в текстовых ответах **не вырезаются**: это честные
  данные респондента. Экранирование делает модуль `csv` сам — значение
  попадёт в ячейку как текст, а не выполнится в Excel.

**Известные ограничения (уйдут в README):**

- Анти-дубль строгий: за общим NAT или корпоративным прокси второй
  участник не сможет пройти опрос.
- Заполненный текст показывается в статистике как превью — имена и контакты
  респондентов не собираются, но в CSV попадает всё, что респондент написал.

## 2026-09-29 — Починка запуска в два клика

`start.bat` из предыдущей записи не работал. Нашлось три независимые
причины, и все три проявлялись только при двойном клике, а не в pytest.

### 1. Русский текст внутри .bat ломает cmd.exe

При запуске `start.bat` окно падало в `pause` с кашей вместо сообщений.
`cmd.exe` читает файл пакетной обработки в системной кодировке, а не в
UTF-8: строки с кириллицей превращались в текст, который cmd пытался
выполнить как команды — в логе шло `'n' is not recognized`,
`'?�����' is not recognized`. Плюс путь проекта содержит и кириллицу, и
эмодзи ⭐, и в команде он рассыпался на `???????` и `\u2b50`, из-за чего
python.exe падал с Permission denied.

Проверено минимальным экспериментом: файл из одних ASCII-символов с
первой строкой `chcp 65001` работает и с кириллицей в пути, и с вызовом
`.venv\Scripts\python.exe`. То есть дело именно в не-ASCII внутри файла,
а не в пути.

Решение: русские сообщения вынесены в `scripts/launcher.py`, а `start.bat`
переписан так, чтобы в нём не осталось ни одного байта выше 0x7F. Чтобы
это не разъехалось снова, добавлен тест-регрессия, который читает файл
побайтово и падает на любом не-ASCII символе.

### 2. Проверка «занят ли порт» давала разные ответы

`scripts/launcher.py:port_is_free` определял занятость через
`socket.connect_ex`. На Windows подключение к незанятому порту возвращает
WSAEWOULDBLOCK и оставляет сокет в полуоткрытом состоянии, поэтому повторная
проверка того же порта давала противоположный ответ: в тесте один и тот же
порт сначала считался занятым, потом свободным. При живом запуске это
означало бы, что сервер то стартует, то отказывается.

Заменено на `bind` без `SO_REUSEADDR` — это и есть ответ на вопрос «сможет
ли сервер занять порт». `SO_REUSEADDR` намеренно не выставляется: на
Windows он позволяет перехватить порт, который уже слушает чужой сокет.

Побочно лаунчер теперь умеет объяснять занятый порт: если 8000 занят, он
не падает, а говорит, что сервер, скорее всего, уже запущен, и
предлагает свободный порт рядом.

### 3. smoke ходил по рабочей базе и копил мусор

`scripts/smoke.py` поднимал сервер на `survey.db` из `.env`. Каждый прогон
оставлял анкету и юзеров: к моменту разбора в рабочей базе было 2 анкеты
и 39 пользователей, все из тестов. Теперь smoke поднимает сервер на своей
`_smoke.db`, гасит сервер и удаляет базу в `finally`, а `engine.dispose()`
идёт перед удалением — иначе на Windows файл остаётся занятым, и `unlink`
даёт PermissionError.

Побочно вылез ещё один баг того же происхождения: исключение из `finally`
проглатывало `sys.exit(main())`, и прогон завершался кодом 1 при нулевом
числе провалов. Теперь уборка не может превратить успех в ошибку.

### Ещё две правки в smoke

- **Источник токена.** Скрипт читал `MODERATOR_TOKEN` из `os.environ`, а
  приложение — из `.env`. После автосоздания `.env` эти два значения
  расходились, и smoke проверял ветку «раздел выключен» у работающего

## Решения, которые стоит помнить

- **Почему `404`, а не `403`.** И для чужой анкеты, и для `/admin`
  неадминистратором. По коду ответа нельзя проверить, существует ли объект.
- **`next` собирается из запроса, а не из параметра.** Иначе `/login?next=…`
  становится открытым редиректом на сторонний сайт.
- **Пароль администратора читается один раз.** `ADMIN_USERNAME` /
  `ADMIN_PASSWORD` нужны только при создании учётки. Сменил пароль через
  `/account/password` — действует новый, а не значение из `.env`.
- **Предупреждение о стандартном пароле можно отложить навсегда.** Это
  явный выбор пользователя, поэтому «продолжить на стандартном пароле»
  ставит `must_change_password = False`.
- **Публичная документация закрыта целиком.** `/docs` описывал и закрытые
  процессы, поэтому схема переехала в `/admin/openapi.json`.

**Решения:**

- **Оценка требует точного совпадения всего набора** у вопроса с несколькими
  вариантами. Частично верный набор не считается верным: иначе один балл
  означал бы разные вещи в разных анкетах.
- **Свободный текст и вопросы без отметки в балл не входят.** Нечего
  оценивать — иначе знаменатель «из 5» врал бы респонденту.
- **Включить проверку, когда оценивать нечего, нельзя.** Форма отвечает
  ошибкой и просит отметить правильный ответ, вместо того чтобы отдать
  респонденту пустую страницу итога.
- **Режим можно переключить даже на замороженной анкете**, где структура
  вопросов уже не меняется: режим относится к анкете, а не к вопросу. Но
  оцениваемость тогда считается по базе, а не по пришедшей форме.
- **Правильные ответы хранятся текстом варианта, а не идентификатором.**
  Смена текста варианта разрывает связь, и это осознанно: привязка по id
  требовала бы переписывания статистики при каждом редактировании вопроса.

## 2026-09-30 — Путь к базе привязан к корню проекта, а не к папке запуска

Разбирался вопрос: что за файлы `survey.db-wal` и `survey.db-shm` рядом с
базой и зачем они в корне. По ходу нашёлся настоящий баг.

**Что это за файлы.** Включён `PRAGMA journal_mode=WAL` в
`database/session.py:38`, поэтому SQLite держит рядом журнал изменений
(`-wal`) и служебный индекс (`-shm`). Файлы штатные и удалять их «напрямую»
нельзя: в режиме WAL подтверждённые изменения лежат в журнале до чекпойнта.
Проверено на копии: после мягкого закрытия `survey.db` вырос со 114 КБ до
160 КБ, а `-wal`/`-shm` исчезли — значит в журнале было около 45 КБ реального
содержимого. Строки при этом сохранились (406 до и после, `integrity_check:
ok`). Все три файла уже закрыты `.gitignore`, в коммит не попадут.

**Баг: база лежала по относительному пути.** В `core/config.py` стояло
`database_url = "sqlite:///./survey.db"`. SQLite разрешает такой путь
относительно рабочей папки процесса, а не корня проекта. То есть запуск из
соседнего каталога молча создавал **вторую пустую базу**, а снаружи это
выглядело как «все анкеты пропали», хотя настоящая база лежала рядом
нетронутая. `.env` и картинки давно привязаны к `BASE_DIR`, база осталась
последней относительной. Усугублял дело `.env.example`, который сам
подсказывал `DATABASE_URL=sqlite:///./survey.db` — скопировавший пример
возвращал баг обратно.

До этого проверил штатные способы запуска: `start.bat` делает
`cd /d "%~dp0"`, а Docker задаёт абсолютный `sqlite:////data/survey.db` на
volume. Эти пути попадали в корень верно, поэтому баг и не всплывал — он
срабатывал только на ручном запуске из чужой папки.

**Сделано:**

- **`default_database_url()`** — путь строится от `DB_PATH = BASE_DIR /
  "survey.db"`. Три слэша перед путём — требование SQLAlchemy: так
  абсолютный путь в POSIX получает четыре слэша, а в Windows с буквой
  диска — три, и оба указывают на один файл. Кириллица и пробелы в пути не
  кодируются, поэтому разбор пути в `_is_sqlite_file()` не ломается.
- **Явный `DATABASE_URL` по-прежнему главнее.** Если переменная задана, она
  берётся как есть: внешнюю базу этим и задают. Для этого поле стало
  `Field(default_factory=default_database_url)`, а не жёсткой строкой.
- **Шаблон `.env` больше не подсказывает относительный путь** и прямо
  предупреждает: указывать только ПОЛНЫЙ путь, иначе с другого каталога
  появится вторая база.
- **Путь к базе печатается в `init_db`** — теперь это полный путь, и до
  какого файла реально дошло, видно сразу.

**Проверено:**

- `pytest -q` - 593 passed (было 586, добавлено 7).
- Новый `tests/test_config_paths.py` (7 тестов): путь лежит в корне проекта,
  он абсолютный, не зависит от `cwd`, явный `DATABASE_URL` побеждает,
  без переменной берётся значение по умолчанию, шаблон `.env` не задаёт базу
  молча и предупреждает про относительный путь.
- `python -m scripts.smoke` - 108 из 108.
- **Запуск из чужой папки.** Из пустого каталога вне проекта открылась
  именно база проекта (`Path(opened).resolve() == DB_PATH.resolve()`),

## 2026-09-30 — Смена пароля выкидывает из всех устройств, кроме текущего

Пункт из разбора качества: cookie сессии подписана, но на сервере не хранится,
поэтому смена пароля её **не обесценивала**. Старый телефон продолжал работать
под паролем, который уже не действует, ещё месяц (срок жизни cookie — 30
дней). Для учебного проекта это заметная дыра, и на защите про неё спросят.

**Сделано:**

- **Колонка `users.password_changed_at`** — момент последней смены пароля.
  Пустая у тех, кто пароль не менял, и это осознанно: иначе перенос базы на
  новую версию выкинул бы из сессии всех сразу. Миграций у проекта нет, и
  колонка дописывается сама через `add_missing_columns()`.
- **`resolve_current_user()` сверяет момент подписи cookie с этой отметкой.**
  Cookie, подписанная раньше, больше не пускает — ни в кабинет, ни к анкетам,
  потому что доступ везде проверяется одним и тем же способом.
- **Текущую сессию не выбиваем.** Смена пароля обесценивает все ранее выданные
  cookie, включая текущую, поэтому в ответе на смену пароля cookie
  перевыдаётся: иначе человек, только что сменивший пароль, вылетел бы на
  страницу входа и решил бы, что его выкинули отовсюду сразу.

**Две ошибки, на которые ушла большая часть времени. Обе проявлялись
одинаково — «после смены пароля выкинуло даже из своего браузера»:**

1. **Часовой пояс.** Из SQLite приходит naive-datetime, а `utcnow()` кладёт в
   базу UTC, и машина здесь UTC+3. Наивное сравнение считало подпись cookie
   «на три часа старше» отметки о смене. Теперь момент из базы явно
   приводится к UTC: `_as_utc()`.
2. **`itsdangerous` обрезает микросекунды.** В подписи `22:08:38`, а в отметке
   о смене `22:08:38.057701` — тот же самый момент оказывался «раньше» на
   58 миллисекунд. Поэтому обе стороны сравниваются **по целой секунде**:
   `_whole_second()`. Отсюда честное ограничение: cookie, подписанная в ту же
   секунду, что и смена пароля, остаётся действительной. Обойти это нельзя —
   такой точности просто нет в подписи.

Допуск «на пару секунд» сначала выглядел логичным, но, как показал тест
границы, он открывал окно, в котором старая cookie продолжала работать, —
то есть сам отменял смысл правки. Сравнение по секундам точнее и не оставляет
дыры шире, чем позволяет формат подписи.

варианты, и все они отпадают по существу, а не по цене:

- **Vercel, Render и подобные** — serverless без постоянного диска под
  приложение. База SQLite и загруженные картинки живут на диске, значит в
  таком окружении их не удержать. Понадобились бы внешняя база и объектное
  хранилище — это переделка проекта, а не настройка.
- **Бесплатные тарифы облаков с виртуальной машиной** — лимиты на память
  маленькие, а провайдеры зарубежные принимают только зарубежную карту.
- **PythonAnywhere Free** — не подходит по существу: приложение на ASGI, а
  хостинг запускает WSGI, и бесплатный тариф ограничивает CPU считанными
  секундами в сутки, чего живому сайту не хватит.
- **Бесплатный хостинг сайтов** (Apache, PHP) — там не запускается
  Python-сервер с состоянием.

Поэтому в тексте предложены два рабочих варианта: локальная сеть как основной
и туннель для ссылки в интернете, с честным перечислением ограничений. Такое
описание не устареет и не требует проверки тарифов.

**Проверено:**

- **Аудит README скриптом:** все якорные ссылки ведут в существующие разделы,

## 2026-10-01 - Туннель одной кнопкой: `start_tunnel.bat`

**Сделано:**

- Новый `start_tunnel.bat` запускает сервер и туннель Cloudflare вместе, в одном
  окне. Обычный `start.bat` не тронут и остаётся отдельным файлом.
- Новый `scripts/tunnel.py`:
  - ищет `cloudflared` в `PATH` и в `C:\Program Files (x86)\cloudflared`;
  - запускает Uvicorn в потоке и `cloudflared tunnel` в подпроцессе;
  - читает stderr туннеля, вылавливает публичный адрес и печатает его крупно
    в рамке;
  - гасит туннель перед сервером, ловит `Ctrl+C`;
  - не поднимает туннель, если порт 8000 занят, и подсказывает свободный.
- Скрипт ждёт, пока адрес реально начнёт отвечать, и только потом пишет
  «Ссылка отвечает, можно открывать» и открывает браузер.

**Найдено и исправлено:**

- `Popen` получал имя `cloudflared` без пути, а папка установки не в `PATH`:
  `WinError 2`. Теперь передаётся найденный полный путь.
- Событие «адрес найден» ставилось до печати рамки, из-за чего строки после
  адреса наезжали на него. Событие перенесено в конец.
- Протокол задан явно: `--protocol http2`. По умолчанию cloudflared идёт по QUIC
  через UDP 7844, который домашние и мобильные сети часто режут.
- Сигнатура `read_tunnel_url` не совпала с вызовом: `TypeError` в потоке,
  адрес не появлялся, скрипт висел до таймаута. Исправлено.

**Проверено:**

- Сервер поднимается, локальный `/health` отвечает 200.
- `cloudflared 2026.9.3` выдаёт адрес за 8-10 секунд, пишет
  `Registered tunnel connection ... location=dme01 protocol=http2`.
- Публичный адрес отдаёт 200 на `/health`: `{"status":"ok","app":"ЧЕСТНО",
  "version":"1.0.0"}`, страницы `/` и `/login` открываются.
- Проверки самого cloudflared: DNS PASS, QUIC PASS, HTTP/2 PASS, edge API PASS.
- Порт 8000 и процессы `cloudflared` после проверок закрыты, ничего не висит.

**Важно про надёжность (ограничение сети, не баг приложения).** Замеры на этой
машине, обычный интернет без VPN:

- дефолтный QUIC не регистрируется совсем: `Register tunnel error from server
  side: context deadline exceeded`, затем `initial tunnel connection failed`;
  поэтому в скрипте явно задан `--protocol http2`, он регистрируется всегда;
- с HTTP/2 туннель регистрируется (`Registered tunnel connection ...
  location=dme01/dme06`), но соединение с краем Cloudflare рвётся каждые
  40-170 секунд: `Error shutting down control stream: client disconnected`,
  затем `Retrying connection in up to 2s` и повторная регистрация;
- в эти паузы (10-20 секунд) публичная ссылка отдаёт 530, а после полного
  обрыва - 1033 с текстом «Cloudflare is currently unable to resolve it»;
- первое подключение занимает 20-90 секунд, в это время тоже 530, поэтому
  скрипт ждёт готовности и открывает браузер только на рабочем адресе;
- `--ha-connections 4` не помогает: края всё равно регистрируется одна связь
  `connIndex=0`, и обрывается именно она;
- отдельно проверено, что дело не в протоколе IP: и `-4`, и `-6` дают
  одинаковый результат.

Итог: сайт и скрипт работают, ссылка становится рабочей, но на этой сети
Cloudflare рвёт соединение. Практический вывод для проверки - другой канал
интернета (VPN или мобильная точка доступа) либо раздача адреса локальной сети
из `start.bat`. Всё это описано в README.

**Не сделано:** тесты для `scripts/tunnel.py` не добавлены: модуль работает с
внешним процессом и сетью, поэтому покрыт только ручной прогон. Проверка на
другой сети остаётся за пользователем.

## 2026-10-01 - Запуск на чужом компьютере без Python

**Задача:** проект должен запускаться на ноутбуке, где человек не
программирует и Python не установлен, одним двойным кликом.

**Сделано:**

- Новый `scripts/install_python.ps1`: молча ставит Python 3.12.10 с python.org
  без прав администратора (`InstallAllUsers=0`, установка в
  `%LOCALAPPDATA%\Programs\Python\Python312`). Сам выбирает amd64 или arm64 по
  `PROCESSOR_ARCHITECTURE`, идемпотентен, качает во временную папку, удаляет
  установщик после успеха. Только ASCII: Windows PowerShell 5.1 читает `.ps1`
  без BOM в ANSI-кодировке, и русский текст превратился бы в мусор.
- `start.bat` и `start_tunnel.bat`: новая подпрограмма `:find_python` ищет
  подходящий интерпретатор (`py -3.12`, затем `py -3`, затем `python`),
  берёт версию 3.12 или новее, и только если ничего нет - зовёт установщик.
  Значение может содержать аргументы (`py -3`), поэтому нигде не
  заключается в кавычки как в путь.
- Нумерация шагов `[1/3] [2/3] [3/3]`, общая ветка `:have_venv` для быстрого
  повторного запуска.
- README: раздел «Передать другому человеку» с четырьмя шагами, таблицей
  «что уже учтено», оговорками про пустую базу и `cloudflared`. В «Запуск за
  10 секунд» убрано требование установленного Python.

**Почему так:** `.env` со случайным `SECRET_KEY` и база через `create_all()`
создаются сами, `requirements.txt` уже зафиксирован и подходит как есть. Единственным
препятствием был отсутствующий Python, поэтому и сделана только его установка.
Обновлять `requirements.txt` не нужно.

**Проверено:**

- Ссылки на установщик существуют для 3.12.10: amd64 и arm64, HTTP 200,
  25.7 МБ.
- Скачивание: 25.72 МБ за 22 секунды, сигнатура файла `MZ` - настоящий
  исполняемый файл, проверка размера (а вредоносная HTML-страница под именем
  `.exe` отсекается порогом 10 МБ) срабатывает корректно.
- Синтаксис `.ps1` разбирается без ошибок; повторный запуск при уже
  установленном Python выходит с кодом 0 и ничего не качает.
- Поиск Python: при системном Python возвращает `python`, при урезанном `PATH`
  - `NOT_FOUND`. Фильтр версии отдельно проверен на 3.9, 3.11, 3.12, 3.13 и
  3.14: первые два отвергаются, остальные принимаются.
- `start.bat` на машине с готовым окружением: печатает `[3/3] Starting.`,
  отдает `200` на `/health`. Порты и процессы после проверки закрыты.

**Известные ограничения:** автоустановка Python требует интернет и работает
только на Windows. Первая установка зависимостей тоже из интернета, так что
офлайн-сценарий не поддерживается - для него нужен один `.exe`, собранный
PyInstaller.
